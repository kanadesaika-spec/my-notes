# 08_GitHubを使ってソースを管理しよう【実践】（課題3-08）

## このページはなにを学ぶpage？
Git（バージョン管理ツール）とGitHub（ソースの保管・共有場所）で、作ったプロジェクトの**変更履歴を記録し、いつでも過去の状態に戻せる**ようにする方法を学ぶ。コマンドを覚える必要はなく、Claudeに日本語で伝えるだけで進められる。

## 重要ポイント
### コマンドの代わりに覚える「操作キーワード」
難しいGitコマンドの代わりに、この日本語だけ覚えればよい：
| 言葉 | 何が起きるか |
|---|---|
| 「gitでソースを管理して」 | フォルダがバージョン管理された状態になる |
| 「リモートリポジトリをプライベートで作成してプッシュして」 | GitHub上に非公開の保管箱ができてアップロードされる |
| 「コミットして」 | 変更を記録する（セーブポイント作成） |
| 「プッシュして」 | 変更をGitHubに反映する |

### 安全上の最重要ポイント
- **必ず「プライベートリポジトリ」（非公開）と明示して作らせる**。パブリック（公開）で作ると開発ソースが世界中から見えてしまう。

### 初期設定でつまずいたときの流れ
1. gh CLI（GitHub CLI）の導入を提案されたら「gh CLIをインストールしてください」でOK
2. 認証にはトークン（アクセス用の合言葉）が必要な場合がある：
   - https://github.com/settings/tokens/new でトークンを発行
   - 名称と期限を設定し、「repo」にチェック→Generate token
   - 表示されたトークンをコピーしてClaudeのチャットに貼り付ける
3. 初めてのpush時はブラウザが開いてGitHubログインを求められる→作ったアカウントでログイン

### GitHubアカウント作成の注意
- ユーザーネームは半角英数字で、**GitHubのURLに入る大事な部分**なので慎重に決める。
- Claude Codeデスクトップアプリ導入時に入れる「Git」と「GitHub」は別物（Gitは道具、GitHubはサービス）。

### さらに学べる基礎知識（ページ内に章立てあり)
ブランチ操作／プルリクエスト（PR）／Issue（課題管理）／フォークとクローン／GitHub Projects／Git worktree／チーム開発のベストプラクティス など。

## 用語解説
- **Git（ギット）**：ファイルの変更履歴を記録する「バージョン管理ツール」。ゲームのセーブデータのように、いつでも過去に戻れる。
- **GitHub（ギットハブ）**：Gitで管理したソースをインターネット上に保管・共有できるサービス。
- **ソース（ソースコード）**：プログラムの中身のファイルのこと。
- **バージョン管理**：「いつ・誰が・何を変えたか」を記録し、過去の状態に戻せるようにすること。
- **リポジトリ**：プロジェクトごとの保管箱。ローカル（自分のPC内）とリモート（GitHub上）がある。
- **コミット**：変更内容を「記録」すること。変更のセーブポイント。
- **コミットメッセージ**：そのコミットで「何を変えたか」を書くメモ。後から履歴を見返すときに重要。
- **プッシュ（push）**：ローカルの記録をGitHub（リモート）へ送って反映すること。
- **プライベート／パブリックリポジトリ**：非公開／公開の保管箱。仕事のソースは基本プライベート。
- **トークン**：パスワードの代わりに使う「アクセス用の合言葉」。他人に見せてはいけない。
- **gh CLI（GitHub CLI）**：GitHubをコマンドで操作する公式道具。Claudeが裏で使ってくれる。
- **ブランチ**：作業用の「枝分かれ」。本体を壊さずに新機能を試せる。
- **プルリクエスト（PR）**：「この変更を本体に取り込んでください」というお願い＋レビューの仕組み。チーム開発の中心。
- **Issue（イシュー）**：バグや要望を記録する「課題チケット」。

## マネタイズへのヒント💰
- **納品物の変更履歴管理は、受託開発の信頼の土台**。「いつ何を変えたか」を示せると、修正依頼・トラブル対応がスムーズになる。
- プライベートリポジトリ運用を知っていれば、お客様のソースを安全に預かる体制を説明できる（法人案件の必須条件になりがち）。
- GitHubは実績の公開場所（ポートフォリオ）としても機能する。公開してよいものはパブリックにして営業材料にできる。
